## Project

A PHP website served at `sys.localhost`: a system and network admin tool for multiple servers and websites. Its focus is tracking statistics and performance, plus continuous monitoring and testing of various parameters. Targets it examines include PHP stacks and MariaDB servers. MariaDB health monitoring includes detecting crashed tables, and connects through PDO (`pdo_mysql`, required in `composer.json`).

Apache serves it on port 5015 (`/etc/apache2/sites-enabled/002-sys.conf`, `ServerName sys.localhost`, DocumentRoot `public/`), and cron runs `php leaf app:run-checks` from this working copy every minute, so changes are live immediately, including in the scheduler: **migrate the live database (`php leaf db:migrate`, after a backup: `mariadb-dump` of the saved connection's database, or a copy of the SQLite file while it's still on SQLite) as soon as a schema change is in the working tree**, or the next request or cron run hits the missing columns. **The live site holds real accounts.** Never run end-to-end tests, failed logins or setup flows against it or its database. Use a throwaway database on a separate dev server instead (the env var overrides `.env`):

```bash
echo '{"driver": "sqlite", "database": "/tmp/e2e.sqlite"}' > /tmp/e2e-connection.json
touch /tmp/e2e.sqlite && DB_CONFIG=/tmp/e2e-connection.json php leaf db:migrate
mkdir -p /tmp/e2e-views
mkdir -p /tmp/e2e-sessions
DB_CONFIG=/tmp/e2e-connection.json VIEWS_CACHE_PATH=/tmp/e2e-views SESSIONS_PATH=/tmp/e2e-sessions php -S localhost:5599 -t public public/index.php
```

`DB_CONFIG` points the app at another connection file (see Database). **`DB_DATABASE=...` no longer redirects the app** once `storage/app/db/connection.json` exists: always use `DB_CONFIG`. A `DB_CONFIG` naming a missing file gives the install wizard (to test it, run the server from a copy of the app, since the wizard offers to copy `storage/app/db/database.sqlite`).

Always pass `VIEWS_CACHE_PATH` (read in `config/app.php`): the dev server runs as your user, and compiled Blade views it leaves in `storage/framework/views` break the live site. When a view changes, Blade on the live site (`www-data`) `touch()`es the unchanged compiled file, which only its owner may do ("touch(): Utime failed: Operation not permitted"). If it happens, delete `storage/framework/views/*.php`; they're rebuilt on the next request. The same goes for any scratch script that loads the app's config (`Leaf\Core::loadApplicationConfig()`) to render a view: `putenv('VIEWS_CACHE_PATH=<scratch dir>')` before it, since its Blade compiles through the config's cache path whatever directory you pass it.

To test SSH and MySQL code for real, run a throwaway `sshd` and MariaDB as your own user on high ports (never touch the system ones): `ssh-keygen` a host key into a scratch dir and start `/usr/sbin/sshd -D -e -f <config>` with `ListenAddress 127.0.0.1`, `Port 2299`, `HostKey`/`AuthorizedKeysFile`/`PidFile` in the scratch dir, `UsePAM no`, `StrictModes no`; and `mariadb-install-db --no-defaults --datadir=<dir>` then `mariadbd --no-defaults --datadir=<dir> --socket=<dir>/mysql.sock --port=3399 --bind-address=127.0.0.1`, creating a user over the socket with `mariadb -S <sock> -u $(whoami)`.

**Subdirectory installs** (e.g. `/var/www/html/sysadmin/` at `/sysadmin`; README "In a subdirectory of another site"): `App\Utils\BasePath` works out the base in `public/index.php` (`detect()`: `SCRIPT_NAME` `/sysadmin/public/index.php` for a `/sysadmin/...` request means `/sysadmin`, the top-level `.htaccess` having sent it into `public/`; an Alias to `public/` gives the script's own directory; a site root and `php -S` give `''`; `SetEnv APP_BASE_PATH` overrides). With a base: Leaf's router gets it (`app()->setBasePath()`, so routes match without it, and `response()->redirect('/x')` adds it), and an output buffer rewrites the app's HTML and JSON (`rewriteOutput()`: `href`/`src`/`action`/`formaction`/`data-paged` values starting with one `/`, string literals in inline scripts starting with an app path segment (`PREFIXES`), `<html data-base>`, and a JSON `redirect`; form `value`s, `data-path` and other text are left alone). So **keep writing root-relative app paths** (`/mariadb/query`) in views and controllers; use `BasePath::path()` for the request path the routes see (layout menus, `Authenticate`, `RequireDatabase`), and in `public/assets/js` prefix fetches with `document.documentElement.getAttribute('data-base') || ''` (as `passkeys.js` and `fail2ban.js` do); a new first path segment goes in `PREFIXES`. The session cookie becomes `sysadmin_session` with path `/sysadmin/`; this machine's Apache helper is off (`LocalApacheService::inSubdirectory()`: its guard against disabling the site serving the app can't work there). At a site's root (this install) nothing is rewritten. Leaf's `XSRF-TOKEN` cookie is off everywhere (`config/csrf.php`; the scripts read the hidden field). Tested with a real Apache as the test user (stand-in main site, app symlinked at `html/sysadmin`, scratch DB via `SetEnv DB_CONFIG`): sign-in, all 27 menu pages, paged tables, a POST, sign-out, no request outside `/sysadmin`, and `.env`/`storage`/`vendor`/`config`/`.git` all 404.

**Errors are recorded** (`App\Services\ErrorRecorder`, a Leaf crash reporter registered in `public/index.php` with `crash()->reportTo()`, delivered after the response, never throws): each uncaught error gets `storage/errors/<request id>/` (`ERRORS_PATH` overrides; gitignored; kept `KEEP_DAYS` = 30, pruned as new ones are written) with `report.json` (Leaf's report: exception, cause chain, frames with source excerpts but no argument values, breadcrumbs, timings; plus `request_details`: method, path, base path, route path, query, form, a JSON body, uploaded file names, headers, client, signed-in user; and `environment`: server, PHP, commit from `.git`) and `report.md`. The ID is mod_unique_id's (`UNIQUE_ID`/`REDIRECT_UNIQUE_ID`, as in the access and error logs), else `sys-<date>-<time>-<random>`. Secrets are masked: keys by Leaf's `Redactor` plus `EXTRA_SECRETS` (code, otp, credential, passkey, csrf, key…), and text by `scrub()` (values given to secret-sounding columns or fields, e.g. a SQL error's filled-in query, and Argon2/bcrypt hashes). With `APP_DEBUG` off the error page is Leaf's production page saying "recorded as <ID>" (`ErrorRecorder::page()`, `app()->setErrorHandler()` in `app/routes/index.php`); with it on, Leaf's debug page. Errors before Leaf's config loads (e.g. an unreadable connection file) are recorded too, shown with Leaf's plain page. Tested: a real failing request on the live site and on a debug-off dev server (page shows the ID, the report is written, a `?password=` in the URL masked).

Apache runs as `www-data`: `storage/` must stay group `www-data`, group-writable, with setgid on its directories, or the database and Blade cache writes fail with a 500.

## Framework: Leaf MVC

The app is built on **Leaf MVC v5** (leafphp.dev). **When Leaf MVC best practice conflicts with any other convention in this file, Leaf wins**, except for the security rules below.

- Code lives in `app/` under `App\`, in Leaf's type-based folders (`app/controllers`, `app/models`, `app/routes`, `app/views`, `app/services`, `app/middleware`, ...). The PSR-4 mappings are already in `composer.json`.
- Controllers stay thin. Business logic (auth, user management, monitoring checks, MariaDB probes) goes in service classes in `app/services` (`App\Services\`).
- Models extend `App\Models\Model` (Eloquent via `Leaf\Model`). Database schemas are YAML files in `app/database/` and are the source of truth; apply them with `php leaf db:migrate`. Which database they go to is the saved connection (see Database); `storage/app/db/database.sqlite` is the SQLite file from before, kept as a backup and offered for copying.
- Exceptions live in `app/exceptions` (`App\Exceptions\`, a mapping added to `composer.json`); security failures extend `SecurityException`.
- Route partials are `app/routes/_*.php` and are loaded automatically. Views use Blade (`app/views/*.blade.php`, layout `layouts/app`); styling is plain CSS in the layout.
- `config/database.php` (published with `php leaf config:publish database`) takes its default connection from `App\Utils\DatabaseConfig` (see Database): the saved connection (`app`), else a legacy `DB_CONNECTION` from `.env`, else `unconfigured` (in-memory SQLite, never queried: `RequireDatabase` sends everything to the wizard), so a missing `.env` can't send migrations to a local MySQL server's `forge` database. `php leaf key:generate` without a `.env` reports success but saves nothing. On web requests, `App\Utils\AppKeyBootstrap` (called from `public/index.php` before Leaf loads `.env`, because the CSRF module needs the key at boot) creates `.env` from `.env.example` and generates `APP_KEY` if missing, under a lock so concurrent first requests agree on one key. If it can't write `.env`, it stops with a 500 rather than run on a key that would be lost. It also exports the key into the process environment: `php leaf app:start` loads `.env` into its own environment and the built-in server inherits it (possibly with an empty `APP_KEY`), and Leaf's `.env` loader never overrides an existing variable, so otherwise every request would fail with "No CSRF secret is set" until a restart. Default `APP_URL` is `http://localhost:5500/` (matches `leaf serve`).
- CSRF protection is on for every POST (`leafs/csrf`); every form needs `@csrf`. `config/auth.php` exists only because Leaf MVC reads `auth.session` to decide whether to enable CSRF and errors if it's missing.
- The `hidden` attribute loses to any CSS `display` (grids, flex); the layout's `[hidden] { display: none !important; }` keeps it working. Menu items highlight the most specific matching path (`/ssh/reports` is Reports, not also Test).
- Route middleware (`app/middleware`) passes data to controllers with `response()->next([...])`; controllers read it with `$this->request->next('auth')`. `Authenticate` (and its subclass `RequireAdmin`) provide an `AuthContext` (the signed-in user).
- Leaf pitfalls hit so far:
  - `request()->get($key)` HTML-escapes by default; pass `false` for passwords and other raw input. `request()->validate()` returns raw values.
  - Leaf validation rules are single-line regexes (`min:1` fails on multi-line input). Check such fields manually.
  - `Response` treats a `Content-Disposition: attachment` header as a file path to stream from disk. For in-memory downloads, send that header with `Leaf\Http\Headers::set()`.
  - `request()->getIp()` trusts client-supplied `Client-IP`/`X-Forwarded-For` headers. Use `Controller::clientIp()` (`REMOTE_ADDR`) for anything security-related.
  - Route-level `middleware` **replaces** a group's middleware instead of adding to it, and a middleware list only accepts callables or named middleware (class-name strings in a list are silently dropped). Routes needing two middlewares use a list of closures (see `app/routes/_admin.php`).
  - Leaf turns PHP warnings into exceptions (500s), so check `is_writable()` and similar before calls that may warn.
  - `Leaf\Controller` has public `render()`, `auth()` and `view()` methods; don't name controller actions or helpers that.
  - In Blade, `@{{` is an escape that prints a literal `{{`, so `{{ $a }}@{{ $b }}` breaks. Concatenate inside one echo instead: `{{ $a . '@' . $b }}`.
  - A Blade directive glued to a letter or digit (`days@if (...)`) isn't compiled and prints literally. Put a space or newline before it.
- Times are stored in UTC (PHP's default here). Show them with `App\Utils\LocalTime::format()`, which converts to `APP_TIMEZONE` from `.env` (America/Los_Angeles on this machine). Don't call `->format()` on a stored time directly in a view.
- Write everything as object-oriented as possible, within Leaf's conventions. Don't add global functions, global variables or procedural logic beyond what Leaf's own entry points (`public/index.php`, `leaf`) and route files require.
- SSH uses **phpseclib 3** (the user's preference). It has no port forwarding, so MySQL is reached over direct TCP only; don't add SSH tunnels without asking.
- Target the server's current PHP (8.3.6 at the time of writing; check with `php -v`). The `sodium`, `pdo_sqlite` and `pdo_mysql` extensions are required.

### Commands

- `composer install` installs dependencies.
- `php leaf app:start` serves the app with PHP's built-in server at `APP_URL` (`--host`, `--port` override; never rewrites `.env`, unlike `leaf serve`). `php leaf app:update` runs `git pull --ff-only`, `composer install` and `db:migrate`, stopping at the first failure. Both are project console commands in `app/console` (auto-registered as `App\Console\<file name>`); run external programs with `Leaf\Sprout\Process` and `setTimeout(null)` (its default is 60 s). Don't use colons inside Sprout option descriptions: they cut the help text off.
- `php leaf list` shows project commands. Use the generators rather than hand-writing boilerplate: `php leaf g:controller`, `g:model`, `g:schema`, `g:middleware`, `g:route`, `g:template`.
- `php leaf db:migrate` applies schema files; `db:seed`, `db:rollback` and `db:reset` also exist.
- `leaf context` prints a compact map of the app.
- Tests, lint and analysis use Leaf's Alchemy (config in `alchemy.yml`; Pest, PHP CS Fixer PSR-12, PHPStan level 5 on `app/`):
  - `composer run test` runs the suite (in parallel). Alchemy writes the PHPUnit config on the fly, so don't call `vendor/bin/pest` directly. To narrow a run, pass a filter regex with no spaces: `vendor/bin/alchemy test --flags=--filter=AuthService` (one file) or `--flags=--filter=one-time` (tests whose names match).
  - `composer run lint` checks style, `composer run fmt` fixes it, `composer run analyse` runs PHPStan.
  - Test files are `tests/**/*.test.php`. `tests/Pest.php` gives every test in `tests/services` a fresh in-memory SQLite database migrated from the real schema files, plus `$this->clock` (a PSR-20 clock tests can move with `advance($seconds)`), `$this->cipher` (a `SecretCipher` with a throwaway app key) and `$this->passwords` (a `PasswordService`). It loads `Leaf\Model` before building the test connection because loading that class connects to the app database and would replace it.

## Database

The app runs on MariaDB/MySQL, PostgreSQL or an SQLite file. **The connection is saved in `storage/app/db/connection.json`** (`App\Utils\DatabaseConfig`; mode 640, group `www-data`; the password encrypted with `SecretCipher`, context `db-password`, so changing `APP_KEY` means setting up again). `DB_CONFIG` names another file (dev servers). Without the file, a `DB_CONNECTION` in `.env` still works (installs from before the wizard; not when `DB_CONFIG` is set); with neither, the app is unconfigured.

- **Install wizard** (`/install/database`, `InstallController`): while unconfigured, the global `RequireDatabase` middleware (`app()->use()` in `app/routes/index.php`) redirects every request there; once configured it's closed (redirects to `/login`). Nobody can sign in yet, so it asks for the **install code** (`App\Utils\InstallCode`: four 5-character groups in `storage/framework/install-code`, printed by `php leaf app:install-code`, deleted after setup): someone who merely reaches a fresh install first can't point it at their own database. On success it flashes what was done on `/login`; a fresh database gets the default admin there as before.
- **`DatabaseSetupService::install()`** (wizard and `php leaf app:db-setup`): if the account given **may create databases and users** (MariaDB/MySQL: a global grant `WITH GRANT OPTION` of ALL, or CREATE + CREATE USER; PostgreSQL: superuser, or CREATEDB + CREATEROLE), it creates the database and **the app's own user with a generated 32-character password**, which can only work with tables there: MariaDB/MySQL `MYSQL_PRIVILEGES` on `db`.* (an existing user gets a new password and `REVOKE ALL PRIVILEGES, GRANT OPTION` first; host `localhost`, `127.0.0.1` or `%` by the server's host); PostgreSQL a `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE` role with CONNECT/TEMPORARY on the database and USAGE/CREATE on `public` only (CREATE on the database, i.e. new schemas, revoked from PUBLIC). The admin account is used only for that and isn't saved; making it the app user is refused (its rights would be revoked). Otherwise the account is used as it is, on an existing database. Then the tables are created from the schema files (a fresh `Manager` set as global, `Schema::migrate()`), an existing SQLite database (`storage/app/db/database.sqlite`, `legacySqlite()`) can be copied in (`copy()`: every table with its ids, 500 rows at a time; refuses a non-empty target unless replacing; PostgreSQL gets real booleans and `setval` on id sequences; counts checked), and only then is the connection saved: a failure leaves the app as it was.
- **App settings shows the connection** (read only, a "Database" card on `/admin/settings/app`; `AppDatabaseService::describe()`): type, where the settings come from, server (a MySQL host of `localhost` means the local socket), database, user, and from the live connection the server version, `CURRENT_USER()`, how it's reached (`PDO::ATTR_CONNECTION_STATUS`), TLS (`Ssl_cipher`) and the app's table count and size. Never the password. This install: MariaDB 10.11 on this machine over the socket, database and user `sysadmin`.
- **`php leaf app:db-setup`** does the same from the shell, e.g. with an admin that logs in over a local socket (`--socket`; the web server can't use yours): defaults from `.env` `DB_HOST`/`DB_NAME`/`DB_USER`, admin = your login (password in `DB_ADMIN_PASSWORD`), copies the old SQLite data unless `--no-copy`, `--replace`, `--force` to set up again. Holds the scheduler lock meanwhile. `app:run-checks` does nothing while unconfigured.
- MariaDB/MySQL connections use `timezone` `+00:00` (TIMESTAMP columns would otherwise convert from the server's zone, e.g. PDT), utf8mb4, strict mode. Column types matter there: `string` is VARCHAR(255) and strict mode refuses longer values, so paths use `length: 1024` (not indexed: index keys are limited to 3072 bytes) and JSON/PEM that may pass 64 KB uses `mediumText`/`longText`.
- Verified: MariaDB 10.11 (throwaway server; the live data copied, read back through the models: times, booleans, JSON, encrypted secrets, ids, emoji) and PostgreSQL 16 (local server, scratch database dropped afterwards); the wizard end to end (wrong code, admin-as-app-user, wrong password, admin account with copy, plain account on its own database).

## Accounts and sign-in

The client decided against encryption at rest: app data is stored in plain SQLite. Git history up to commit `863d3e9` has the earlier encrypted design (master key, key files, registration) if it's ever needed again.

### Rules

1. **Ways to sign in are an admin setting** (App settings, `LoginMethodService`): a **password** the user chose, an **authenticator** app code (TOTP, Google Authenticator defaults), a **passkey or hardware security key** (WebAuthn). Each is Off, Optional or Required (`login_password`, `login_authenticator`, `login_passkey`: 0/1/2; default authenticator required, the others off, i.e. the earlier code-only behaviour). **Required = every user must set it up; signing in takes any one method** the user has that's on (the user's decision: with passwords on, a password alone signs in; the settings page says so). A session is only created after a method is checked, which is why the app doesn't use `leafs/auth`.
2. **Admins create all accounts, with a one-time password they choose.** There is no self-registration. The admin types a one-time password (at least 8 characters, `PasswordService::MIN_LENGTH`, and not 6 digits so it can't be mistaken for a code) and hands it over outside the website. It only opens setup: a session limited to Profile (the `Authenticate` gate sends every other page to `/profile`) where the user sets up every required method (at least one method if none is required), then "Finish setup" (`AuthService::completeSetup()`) discards it (`users.password` = null, `must_change_password` = false). An admin reset ("Reset sign-in") removes **every** method (password, authenticator, passkeys), sets a new one-time password and ends the user's sessions; so does `app:reset-admin`; deleting a user deletes their passkeys.
3. **Existing users missing a required method** (an admin made one required) sign in with another method and are held on Profile by the same gate until they set it up. A user in setup can't sign in with methods, only the one-time password.
4. **At least one admin, and no lock-out.** Demoting or deleting the last admin is refused, and admins can't act on their own account in the admin tools. The settings refuse turning every method off, or levels that would leave an admin who finished setup with no usable method (`LoginMethodService::checkLevels()`, called from `SettingsService::update()`). A user can't remove a required method or their last usable one (`canRemove()`).
5. **Secrets.** One-time passwords and user passwords are Argon2id hashes via Leaf's password helper (`Leaf\Helpers\Password::ARGON2`); user passwords go in `users.login_password` (the `password` column stays the one-time password). **User passwords**: at least `PasswordService::USER_MIN_LENGTH` (12) characters, at least 4 different characters, not containing the username, and not on `app/data/common-passwords.txt` (the 12+ character entries of the NCSC's 100,000 most used, lowercased). **Authenticator secrets** are encrypted: `SecretCipher` with a key derived from `APP_KEY`, bound to `totp-secret:<user id>`, so a copy of the database alone can't generate codes. Changing `APP_KEY` makes every enrolled authenticator unreadable; users would need an admin reset.
6. **Idle timeout.** A session ends after `session_timeout_minutes` without a request (App settings, `/admin/settings/app`, 5–1440, default 30); `AuthSessionService::current()` records `active_at` on each request and `Authenticate` flashes "signed out after N minutes without activity". Sessions live in `storage/framework/sessions` (`configureSessionStorage()`, `SESSIONS_PATH` overrides it for dev servers) with PHP's own GC sized for the 24-hour maximum, because Ubuntu's `sessionclean` deletes sessions in `/var/lib/php/sessions` after php.ini's 24-minute `gc_maxlifetime`, whatever the app's timeout.
7. **Session revocation.** The session holds only the user id and `session_version`. Bumping `users.session_version` signs that user out everywhere; admin resets and `app:reset-admin` do this.
8. **Re-confirming** with any method the user has (`AuthService::confirm()`, rate limited like a sign-in; codes are single-use): revealing a tracked account's password (the reveal form, `partials/confirm`; with a passkey the page confirms over JSON first and the form carries `passkey_confirmed`, a one-use flag good for 60 s), and **changing sign-in methods** on Profile, which needs a sign-in or re-confirmation within `AuthSessionService::CONFIRMED_SECONDS` (10 min; during setup the one-time password counts).

### Sign-in flow (`AuthService`, `AuthController`, `ProfileController`)

- `/login` shows the fields for the methods that are on: username, password, authenticator code, "Sign in with a passkey", and (under "First sign-in?") a one-time password. The form takes one of password or code (`AuthService::attempt()`); unknown users, users without a password, and passwords turned off still cost a hash check. A code is checked against the decrypted secret and its time step recorded in `totp_last_step` so it can't be reused.
- With a one-time password: rate limit check, verify it (unknown usernames still run a hash check), then a normal session limited to Profile by the gate.
- Wrong username, password, code and one-time password all look the same (`InvalidCredentials`).
- **Profile** (`/profile`, the username in the navbar; `ProfileController`, `ProfileService`): set/change/remove the password, set up (QR code from a secret kept in the session, `pendingTotpSecret()`) / replace / remove the authenticator, add (named) / remove passkeys, "Finish setup". Only methods that are on are shown.
- **Passkeys** (`PasskeyService`, `public/assets/js/passkeys.js`, lbuchs/webauthn for parsing): the page gets options from a JSON endpoint (`/login/passkey/options`, `/profile/passkeys/options`, `/profile/confirm/passkey/options`; challenge in the session, one use, 5 minutes) and posts the credential back as JSON with the CSRF token in `X-CSRF-Token`. The ceremony checks are the app's own, because the library only allows http for the RP ID "localhost" and matches hosts by suffix without a dot boundary: exact origin of the page, **https or http on localhost/`*.localhost` only, never an IP address** (`PasskeyService::site()`), RP ID = the page's host (stored as `passkeys.rp_id`; a passkey only works on the host it was made on, so `localhost:5015` and `sys.localhost` differ), user presence **and user verification required** (a passkey alone signs in), signature (openssl, or sodium for Ed25519), and the counter must go up (else a cloned key). Registration uses attestation "none" and excludes the user's existing keys. Sign-in without a username offers discoverable passkeys; with one, its credentials are listed (security keys need that), and for an unknown username or one without passkeys an HMAC-derived fake id stands in so the answer doesn't reveal who exists. Failures are rate limited per IP and per the passkey's owner. Browser-tested with Chromium's virtual authenticator (internal discoverable passkey and a USB non-discoverable key); unit-tested with a software ES256 authenticator in `tests/services/Passkeys.test.php`.

### Rate limiting

- **Attempt limits** (`LoginThrottleService`) for sign-in, setup and re-confirming: 20 failures per IP and 10 per username (any IP, case-insensitive) in a sliding 15-minute window, plus **30 per username per day**. The daily cap matters because a 6-digit code is the only secret at sign-in: with ±1 period there are 3 valid codes, so 30 guesses a day is about a 1-in-11,000 chance per day. A limited request gets HTTP 429 with `Retry-After`, without doing any hashing or code checking, and looks the same whether or not the username exists. A success clears that username's failures but not the IP's. Anyone can lock a username out (15 minutes, or a day after 30 failures) by failing on purpose; `app:reset-admin` clears it. Attempts are stored as SHA-256 buckets in `login_attempts` (kept a day), never the typed username or IP.
- **Concurrency cap** (`LimitConcurrentLogins` middleware, `FileSemaphore` lock files in `storage/framework/locks`; lock files owned by another user are opened read-only, which `flock()` allows) on the routes that hash a password (POST `/login`, `/profile/confirm`, `/profile/password`, `/admin/users`, `/admin/users/{id}/reset-password`): at most 4 Argon2id hashes at once across all Apache workers (64 MiB each). Extra requests get HTTP 503 with `Retry-After: 5`. Controllers call `LimitConcurrentLogins::release()` as soon as the service returns.

### Services (`app/services`)

- `AuthService`: sign-in (`attempt`, `attemptPasskey`), one-time password check (`startSetup`), `completeSetup`, `confirm`, `enrolAuthenticator`, returning a `LoginResult` with a `LoginStatus`; creates the default admin.
- `LoginMethodService`: which methods are on/required, what a user has set up (`enrolled`, `usable`, `missingRequired`, `setUpEnough`, `canRemove`), `checkLevels`.
- `ProfileService`: a user changing their own methods. `PasskeyService`: WebAuthn options, registration and verification.
- `AuthSessionService`: the signed-in session (with `confirmed_at`), one-use passkey challenges, a pending authenticator secret, and the session cookie flags (`Secure`, `HttpOnly`, `SameSite=Strict`, strict mode), set from `public/index.php` because Leaf's CSRF module starts the session during boot.
- `PasswordService`: one-time passwords (hash, verify, policy, discard) and users' own passwords (policy, set, verify).
- `TotpService`: authenticator codes (SHA-1, 6 digits, 30 s), ±1 period for clock drift, replay protection, and a server-rendered QR code so the secret never goes to a third-party QR service.
- `SecretCipher`: `APP_KEY`-based XChaCha20-Poly1305 for authenticator secrets, the SSH private key and stored server/account passwords.
- `UserAdminService`: create accounts, reset sign-in (removes every method), promote/demote, delete (every method re-checks that the acting user is an admin), and `resetFromConsole()` for `app:reset-admin`.
- `LoginThrottleService`: the attempt limits above.

## Tracked accounts

Admins track the logins used on servers, **SSH accounts and database accounts kept apart** (`accounts.service`: `ssh` or `mysql`, see `Account::serviceName()`): SSH accounts at `/admin/accounts/ssh` (SSH menu), database accounts at `/admin/accounts/mariadb` (MariaDB menu). Each is **local** (belongs to one server: a system user or a database user), **LDAP** or **shared** (usable on any server, but only for its own service; `Account::usableFor()`, `AccountService::selectableFor()`). An account in use can't switch service. LDAP/shared rows from before the split (service null) are assigned by `syncServers()`: used only for database logins → database account; used for both → split in two, the copy (password re-encrypted, same dates, rotation and notes) taking over the database logins. Each has the current password (`SecretCipher`, `account-password:<id>`), when it was last reset, a rotation period (days, optional) and notes. `AccountService::status()` says `ok`, `due_soon` (within the `account_warning_days` setting, default 7), `overdue`, `unknown` or `none` (no rotation). Recording a password here doesn't change it on any server; the app tracks passwords, it doesn't set them.

- A server's SSH login and database login are accounts (`servers.ssh_account_id`, `servers.mysql_account_id`): each section of the server form has its own "Log in as", and a plain username becomes a local account of that server for that service. `ssh_username` / `mysql_username` are kept in step with the account (also when an account is renamed). When SSH setup succeeds with a password, it's saved as that account's current password; a MySQL password typed on the server form becomes the database account's current password (blank keeps the stored one). `account_server.last_used_at` records when the app last logged in with it (`SshService`, `MysqlService`); SSH and database use of one account on one server share that row.
- Revealing a password needs a fresh authenticator code, is logged in `password_reveals` (who, when) and is sent with `Cache-Control: no-store`. An account a server still logs in with can't be deleted.
- **Origins**: every account records where it came from (`accounts.origin`: `manual` with `origin_user_id`, `server` with `origin_server_id` when created from a server's login settings, `import` with both plus `origin_detail`); null means it predates origin tracking. Shown on the account page and as the list's Origin column.
- **Import users** (MariaDB › Accounts, `AccountService::importMysqlUsers()`, POST `/admin/accounts/mariadb/import`): reads `mysql.user` (via `SELECT *`, so MariaDB's `is_role` and MySQL alike) over the server's MariaDB login and tracks **only `'name'@'%'` users** (the user's rule; other hosts and roles are ignored and counted) as local database accounts of that server. **No password is imported, and an imported account without one can't log in** (`Account::canLogIn()`, checked by `usableFor()` and the server form); recording a password, or typing it on the server form, makes it usable. Imported accounts aren't linked as "used on" until a server logs in with them.
- `syncServers()` (run when the Accounts page loads) gives every SSH and database login an account and moves passwords stored on servers before accounts existed (`ssh-password:<server id>`, `mysql-password:<server id>`) into them. Until then `ServerService::mysqlPassword()` falls back to the server's legacy column.

## Settings

App-wide settings live in the `settings` table (key/value) behind `SettingsService`, which holds each setting's default (`DEFAULTS`), range, which area's page shows it (`SECTIONS`) and warning-below-critical pairs, so adding one needs no schema change (add it to `SECTIONS` too; a test checks every setting is on exactly one page). Admins edit them per area at `/admin/settings/{ssl,ssh,mariadb}` (each area's Settings menu item; `/admin/settings` redirects to SSH). Settings: SSL `ssl_warning_days` (default 7); SSH `disk_warning_percent` / `disk_critical_percent` (85 / 95) and `account_warning_days` (7); MariaDB connections % (80 / 95), replication lag seconds (60 / 600), buffer pool warn-below % (95) and recent-restart minutes (60). `HealthCheckService::defaultChecks()` / `defaultSshChecks()` pass them to the checks, whose constructors default to the same values.

## Servers

A server is a name and hostname with optional SSH (`ssh_enabled`) and MariaDB/MySQL (`mysql_enabled`); SSL certificates are attached to servers from the SSL pages (see SSL monitoring), and the server form only lists them. `ServerService` validates input and owns the `servers` table. Adding/editing/deleting and SSH setup are `ServerConfigController` (`/admin/servers/...`, admins; `?kind=mysql` starts a database-only server); monitoring is `ServerController` (`/`, `/ssh`, `/mariadb`, `/servers/{id}`; "Run checks now" runs health and SSL checks) and `SslController` (`/ssl`).

- With SSH off, `ssh_username` is `''` and the host key and any stored password are forgotten. `SshService` and `SshSetupService` refuse to contact such a server, before any network traffic; `Server::sshReady()` is `ssh_enabled && host key trusted`. `ServerService` treats a *missing* `ssh_enabled` input key as on, for callers that predate optional SSH.

- **SSH login uses the app's own key.** `SshKeyService` generates one Ed25519 keypair on first use (`ssh_keypairs` table). The private key is encrypted with `SecretCipher` (`ssh-private-key:<id>`) and never shown or downloadable; admins copy the public key (shown on `/servers`) into each server user's `~/.ssh/authorized_keys`.
- **Host keys are verified before logging in** (`SshService`). A different host key from the trusted one stops the connection before any credentials are sent (`HostKeyMismatchException`). Keys are compared by blob (`HostKey::sameKeyAs`), and the trusted key's algorithm is pinned when connecting. Changing a server's hostname or SSH port forgets its trusted key; changing hostname, port or SSH user also forgets any stored SSH password.
- **SSH setup** (`SshSetupService`, `/admin/servers/{id}/ssh-setup`, where "Add server" leads):
  1. Trust the host key: the page shows its `SHA256:` fingerprint (same format as `ssh-keygen -lf`); the admin confirms it, and the key is re-fetched and must still match. **Or verify it through the account** (`host_key_check=login`, `SshSetupService::setUpByLogin()`): log in before trusting (`SshService::connectForVerification()`, which still refuses anything but the key shown), with the app's key first, then, only if password login is allowed, the typed or stored password; read the server's host key files (`hostKeysOnServer()`: `/etc/ssh/ssh_host_*_key.pub` via `sh`, or `%ProgramData%\ssh` via PowerShell on Windows) and trust the presented key only if it's there. The same password login installs the app's key (no second password attempt). It's weaker than an out-of-band check: an active impostor sees the password and can fake the file contents. The page says so. The Windows command is untested against a real Windows server.
  2. Try the app's key. If it works, done.
  3. Only if the server allows password login (`ssh_password_allowed`, **off by default**): log in once with the password the admin enters, or, left blank, the one stored for the server's SSH account ("Log in as") in Accounts; install the key with an idempotent `sh` script (`installCommand()`), and try the key again. A typed password that worked becomes the account's current password; a stored one is used as-is.
  4. If the server still refuses key login, keep using the password (stored as the server's account password, see Tracked accounts) with password login for that server (`ssh_auth = password`).
- **Platform detection:** `ServerPlatform::fromIdentification()` reads the SSH banner (`SSH-2.0-OpenSSH_for_Windows_...` means Windows), which phpseclib has before any login. `SshService::probe()` returns host key and platform from one no-login connection; setup records it in `servers.ssh_platform` (forgotten with the host key). The setup page shows only the matching commands (Windows host keys are in `%ProgramData%\ssh`, and administrator accounts use `administrators_authorized_keys`), both when unknown. The password key install is a POSIX `sh` script, so it's refused on Windows before anything runs. Don't probe this machine's own sshd: it runs fail2ban.
- **No password attempts unless allowed.** This machine (only this one; the other monitored servers don't) runs fail2ban set to ban on the first SSH password attempt. `SshService::connectWithPassword()` refuses (before any network traffic) when the server doesn't allow passwords, and `SshSetupService` checks too; tests cover both guards. phpseclib key logins send only `none` then `publickey`, never a password. Each setup step tries a login at most once. A key login before the key is installed still logs one "Failed publickey", which some fail2ban modes count.
- **MySQL** (`MysqlService`) is PDO over direct TCP with a 5-second timeout. It logs in with the server's database account (see Tracked accounts); the password is write-only on the server form (blank keeps it). Turning MySQL off unlinks the account, which stays tracked.
- **MySQL TLS** (`servers.mysql_tls`): `verify` (default for new servers: chain and hostname checked against the pasted CA in `mysql_tls_ca`, or the system CA bundle), `encrypt` (TLS without checking the certificate) or `off`. Behaviour of PHP's mysqlnd, verified against a real MariaDB:
  - TLS is only turned on when `SSL_CA` is set; `SSL_VERIFY_SERVER_CERT` alone does nothing. So `encrypt` passes the system bundle with verification off.
  - With verification on, the hostname is checked against the certificate (IP SANs work for IP hosts).
  - Asking for TLS from a server without it fails ("server has gone away") instead of downgrading. `MysqlService` also checks `Ssl_cipher` after connecting and refuses an unencrypted session.
  - Every TLS failure surfaces as the same vague error, so `MysqlService::explain()` adds the likely causes.
  - PDO needs the CA as a file: the pasted CA (public) is written to a temp file only while connecting, then deleted. `CaCertificateService` validates and normalises pasted PEM.
  - A DSN host of `localhost` makes PDO use the local Unix socket, not TCP.
- **Testing SSH setup:** a non-root throwaway `sshd` can't check passwords, so the password path is unit-tested with a recording stand-in for `SshService`; the key path and host key trust are tested against a real throwaway `sshd`.
- **Connection test** (`ServerTestService`, admin only): SSH runs `uname -srm`, MySQL runs `SELECT VERSION()`; the outcome is stored in `last_tested_at` / `last_test_ok` / `last_test_message`.

## Health checks

**Scheduled checks:** `php leaf app:run-checks` (`AppRunChecksCommand`, cron every minute on this machine, or `--loop`) runs `ScheduledCheckService::runDue()`: each server whose `check_interval_minutes` (default 5) has passed gets its health checks (`HealthCheckService::runNow()`; the scheduler has no user, so no click cooldown). Certificates have their own schedule: every `ssl_check_hours` (SSL setting, 1–168, default 24, so once a day), a run checks any server whose `last_ssl_checked_at` is missing or older than that (`sslDue()`, `SslMonitorService::checkServer(null, ...)`) and directly served certificates by the same rule (`checkDirectDue()`); "Check now" works any time. After consecutive SSH/MariaDB connection failures a server is retried at 2× the interval per failure, up to `MAX_BACKOFF_MINUTES` (60), so a broken key or password can't trip fail2ban or MariaDB's `max_connect_errors`. A single-slot `FileSemaphore` in `storage/framework/scheduler` stops runs overlapping (not `storage/framework/locks`, which is www-data's and not group-writable). Cron runs as `whiskey`, so its line sets `umask 002` to keep the SQLite journal writable for `www-data`. When testing it, point `DB_DATABASE` at a throwaway database whose servers can't reach this machine's port 22.

`HealthCheckService` also runs a server's checks when someone clicks "Run checks now" on `/servers/{id}` or "Check" on `/ssh` / `/mariadb`: SSH checks if SSH is set up (host key trusted), MariaDB/MySQL checks if MySQL is configured. Servers without trusted SSH are never contacted over SSH. Checks only run on demand (no scheduler yet; `servers.check_interval_minutes`, default 5, is stored for one). Results go to `health_checks` (one row per check per run, kept `RETENTION_DAYS` = 30, pruned on each run); the server's worst status is stored in `last_health_status` for the list page.

- MySQL checks implement `App\Contracts\HealthCheck` and live in `app/services/Checks` (`App\Services\Checks\`). Each queries in `run()` and judges in a pure `evaluate()` that the unit tests in `tests/checks` exercise without a database.
- SSH checks implement `App\Contracts\SshHealthCheck`: each gives read-only shell `command()`s and a pure `evaluate(string $output)`. `HealthCheckService::sshScript()` joins them, with a `@@sys-check:<key>` marker line before each, into one `sh -c` script run in **one SSH session per run** (one login, for fail2ban), and `splitSections()` hands each check its part. A test runs the real script locally with `sh`.
- SSH checks: disk (`df -P`, GNU and BusyBox; space and inodes; admin-set levels, default 85 % / 95 %; skips tmpfs, snaps, loop devices, `/proc`, `/sys`, `/dev`, `/run`), load (5-minute load per core; 1.0 / 2.0), memory (`MemAvailable`, falling back to free + buffers + cached; 90 % / 95 %; swap above 80 % warns). Linux only: without `/proc` they report `unknown`.
- A check must not throw for expected problems: a missing privilege or unused feature returns `unknown` or `ok` with an explanation. If one throws anyway, the service records `unknown` and carries on; a failed connection is a single `critical` "SSH connection" (`ssh`) or "MySQL connection" (`connection`) result, and the other kind of checks still run.
- MariaDB and SSH results are kept apart in the UI (`HealthCheckService::isSshCheck()`, `latestByKind()`, `summary()`, `columns()`): a server may be reachable with the database client only. They share one run and `last_checked_at`.
- **SSH reports** (`/ssh/reports?server=&range=24h|7d|30d`, `SshReportService`) read the stored runs (no extra storage): disk used % per filesystem (from the disk check's `details.mounts`), load 1/5/15 min (`details`) and memory/swap % (`value`, `details.swap_percent`), shown as line charts and a data table. Charts are inline SVG rendered by `App\Utils\LineChart` (no JS library or CDN; axes use `currentColor`, so they follow light/dark). With more than one line, each legend entry is a button that hides/shows its line (struck through when hidden); the layout's script refits the value scale to the lines still shown from each point's `data-v` (LineChart's nice-ceiling rule, capped at a fixed `data-max`, floor `data-min`), and restores the drawing as rendered when all are shown again. Time axis and drag-to-zoom are unaffected. Beyond `HistoryReport::MAX_POINTS` (300) runs, points and table rows are averaged into even buckets (5 minutes to a day), and the page says so.
- **MariaDB reports** (`/mariadb/reports`, `MariadbReportService`) do the same for connections (% of max_connections, counts in the table), InnoDB buffer pool hit ratio (`LineChart` `$min` raises the scale's floor, since it sits near 99%), replication lag (replicas only), crashed tables (charted only when any; buckets keep the worst, so a crash isn't averaged away) and uptime in days (a drop is a restart). Both extend `HistoryReport` (periods, bucketing: `averageSeries()` keeps each bucket's average, max or min) and share the `reports/picker` partial. **Periods**: a preset (`RANGES`) or a chosen start and end: the `reports/period` partial (in every report's picker) has `datetime-local` fields in the app's time zone (sent only once edited, so changing the server keeps a preset rolling), and **dragging across any chart** (`LineChart` puts its time axis in `data-from/to/left/right`; the script is in the layout) reloads the report for that stretch as `?range=START-END` (unix times). `HistoryReport::period()` turns either into the range string (`custom()` reads it back; 10 minutes to 31 days); every report query is bounded by both ends, and bucket sizes follow the span.
- **SSL reports** (`/ssl/reports?certificate=&range=`, `SslReportService`) chart days until expiry from `ssl_checks` (via `SslCheck::binding`): for all certificates one line each at its soonest-expiring place, for one certificate one line per place served (a server still serving an old copy stands out), plus a flat line at `ssl_warning_days`. Buckets keep the lowest days left; the table ("Latest checks") shows each certificate's most recent check in the period **from each place it came from** — the host contacted and the address the connection reached (`details.contacted`/`details.address`, recorded by `SslCheckService::check()` from `stream_socket_get_name()`; `SslCheck::origin()` "host (address):port") — so load-balanced / round-robin servers each serving their own copy get a row each; checks from before origins were recorded are dropped once a newer one from the same host exists (a newer check that failed before reaching an address stays); soonest to expire first (failed checks first), up to `MAX_ROWS`; each check's result folds out in a row under it (click the row).
- **MariaDB log import** (admins; "Import log" on `/mariadb` rows and the MariaDB report, for servers with MariaDB and SSH set up; `MariadbLogService`, POST `/servers/{id}/import-log`). **Never assume where logs or config live**: the option files are the ones `my_print_defaults --help` lists (only if that tool is missing: the documented `/etc/my.cnf`, `/etc/mysql/my.cnf`), read over SSH with `!include`/`!includedir` followed (`MariadbConfigParser`); `log_error`, `slow_query_log(_file)`, `log_output` and `datadir` come from their server sections ([mysqld], [server], [mariadb], [mariadbd] and versioned variants), relative paths resolve against datadir, and what the files don't set comes from the running server's variables. No `log_error` means stderr, read from the systemd journal by process name (`_COMM=mariadbd + _COMM=mysqld`), not by unit name. One SSH login per import; files are read from the end (`MAX_BYTES`) and **streamed**: `errorEntries()`/`slowEntries()` are generators over the text (no line array) and entries are stored 500 at a time with one insert per chunk, because a 5 MB log parsed all at once exceeds PHP's 128 MB limit (a test guards the peak); `MariadbLogParser` handles MariaDB 10.x, older, MySQL 8, journal and slow-log formats, times converted from the server's `date +%z`; crashes ("got signal/exception") keep their stack trace. Entries go to `mariadb_log_entries` (30 days), deduplicated by a hash that numbers same-second repeats. **Scheduled**: `ScheduledCheckService` imports every `mysql_log_import_minutes` (MariaDB setting, default 60, 0 = off) via `importNow()`, skipping servers whose SSH is failing and not logging into MariaDB when only that is failing (`useDatabase: false`); files are read incrementally from `servers.log_import_state` (inode and byte offset per file; rotation or truncation starts over from the last `MAX_BYTES`; reads stop at the last complete line), the journal from the last import time; `log_import_message` keeps the outcome for the report. The report shows a per-level count chart and the newest 500 entries. Tested for real against this machine's Ubuntu config through a throwaway sshd.
- `HealthStatus::worst()` ranks `unknown` between `warning` and `critical`, so a check that couldn't run is never hidden behind OK.
- Current checks (default levels, admin-configurable under MariaDB settings): server status (a restart within the last hour is a warning), connections (80 % / 95 % of `max_connections`), crashed tables, replication (MariaDB multi-source and MySQL, old and new column names; lag 60 s / 600 s), InnoDB buffer pool hit ratio (warning below 95 %).
- **Query tool** (MariaDB › Query, `/mariadb/query`, everyone signed in; `MariadbQueryController`, `MariadbQueryService`, `QueryAccountService`): one statement run on every server ticked, results collated into one table (a Server column, then columns merged by name across servers; a repeated name within one result gets " (2)"), a per-server outcome line (login used, rows, rows affected, time from the login, or the error), CSV made in the browser from the table. **Each user keeps a private list of database logins** (`query_accounts`, model `QueryAccount`; only the owner sees or uses one — every method checks — not even admins): a name, username, the password encrypted with `SecretCipher` (context `query-account:<user id>:<id>`, never shown again; blank on edit keeps it), and **the servers it's good on**. **Validated on entry**: adding or changing an account tries its login on every server chosen and saves nothing unless all accept it (the page lists each server's answer); Test re-checks a saved one and records the refusals (`refused`), which the query form marks. In the query form each ticked server takes one of the user's accounts that's for it (servers with none can't be ticked); **admins may choose a server's stored account instead** ("stored"; the monitoring login, often overpowered for developers), which the service refuses for non-admins. `MysqlService::connectAs()` (same host/port/TLS checks as monitoring, `MULTI_STATEMENTS` off, optional default database; `connect()` wraps it with the stored account). Any statement; one that isn't a plain read (`isRead()`: SELECT, SHOW, DESCRIBE, DESC, EXPLAIN, WITH, VALUES, TABLE after comments) needs the confirm box (checked server side). `max_statement_time` / `max_execution_time` = 30 s, rows per server 1–5000 (default 500), cells cut at 2000 characters, binary shown as hex. **A login refused (1045/1698) by the first server it meets — in a run or a check — isn't tried on the rest** (a mistyped password must not hit every server's fail2ban); 5 wrong-password refusals (1045 only: 1698 means the account doesn't sign in with a password at all, e.g. unix_socket, and the message says how to allow one, `QueryAccountService::NO_PASSWORD_HINT`) in 15 minutes (queries and checks alike, `requireNotThrottled()`) make the user wait. **Admins get a "Clear the wait" button** on that alert (`mariadb/error-alert` partial, POST `/mariadb/query/unthrottle`, `RequireAdmin`; `clearThrottle()` lifts only the admin's own wait by unmarking their recent refusals, and logs "(refused-login wait cleared)"); non-admins don't see it. An account may have no password (blank on add). **A login let in by socket identity is for admins only** (`QueryAccountService::socketIdentity()`: the connection came over the local socket, i.e. host `localhost`, and `SHOW GRANTS FOR CURRENT_USER()` / `SHOW CREATE USER CURRENT_USER()` name `unix_socket` or `auth_socket`): over the socket such a login is this site's own system user (`www-data`), which gets in with any password, so a non-admin is refused when saving or testing the account, in each query run (that server fails, not counted as a wrong password) and in the browser (`requireNotSocketIdentity()`). Verified through Apache as www-data: `www-data` in with no or a made-up password, flagged; `sysadmin` with its password over the same socket, not. Page order: intro, Query, Results and Servers (after a run), recent queries, then the user's accounts; Servers, recent queries and accounts start collapsed (Servers opens when a server failed, accounts when there are none or the add form has an error). The layout opens a closed `<details>` that the URL's #hash points into, so redirects to `#accounts` show it. Every run and check is logged in `mariadb_queries` (user, logins used, servers, statement or "(login check)", may-write, outcome, refused; never a password); the page lists the user's recent ones with "Use". Verified against a throwaway MariaDB.
- **Database users** (MariaDB › Database users, `/mariadb/users`, admins; `DbUserController`, `DbUserManagerService`): create, change and drop MariaDB/MySQL accounts on several servers at once, **only on servers whose monitoring account may** (`canManage()` on `SHOW GRANTS FOR CURRENT_USER()`: `ON *.*` `WITH GRANT OPTION` with ALL or CREATE USER; the others are listed with the reason). ## Apache monitoring

Apache is a third health-check kind (`HealthCheckService::KIND_APACHE`, keys `apache_*`, connection failure `apache`), read **over SSH from Apache's own configuration and log files** (`ApacheService`, run with each server's checks when `apache_enabled` and SSH is set up; `servers.apache_enabled` requires SSH). **Nothing about locations is assumed**, and each part degrades on its own:

- The control program is found by name (`apache2ctl`, `apachectl`, `httpd` via `command -v`); `-S` gives ServerRoot and the main error log (already resolved), `-t -D DUMP_INCLUDES` lists every config file in use, which are read (`ApacheConfigParser`: directives with their `<VirtualHost>`/`<Location>`, quotes, continued lines) for `ErrorLog`, `CustomLog`, `TransferLog`. `${VARIABLES}` resolve from `Define` lines and by matching the main `ErrorLog` template against the path `-S` reports (e.g. `${APACHE_LOG_DIR}`); relative paths are under ServerRoot; piped/syslog logs are noted and skipped. The scan is cached in `servers.apache_config` for `SCAN_MINUTES` (60); "Rescan" on `/apache` forces it. **Where Apache is** (`ApacheService::scan()`): the control program counts as found only if `-S` answers (2.4 prints ServerRoot/Main ErrorLog, 2.2 only vhosts and "Syntax OK"; `ApacheConfigParser::answered()`). Order: the remembered container (`servers.apache_container`, e.g. `podman:apache-image`), the server itself, then running Docker/Podman containers (`docker|podman ps`, names/images mentioning apache/httpd first, at most 20), each tried through `ContainerShell` (an `SshService` whose `exec()` wraps commands in `<runtime> exec <name> sh -c '...'`, so `RemoteLogs` and `ApacheConfigFiles` work unchanged, all in the one SSH login); the one found is remembered and cleared when Apache is turned off. Rootless podman only shows the SSH user's own containers; "permission denied" from docker is reported (needs the docker group); no sudo. In a container, logs that are really its output (`/proc/self/fd/1|2`, `/dev/stdout|stderr`, or a symlink to them, checked one `readlink` level deep, never `readlink -f`, which would resolve the exec shell's own pipes) are read on the host with `<runtime> logs --timestamps` (`--tail 20000` first, then `--since` the last line's timestamp, skipping lines at or before it), stdout and stderr separately; other non-regular files are skipped (reading a FIFO would hang). **Apache 2.2** (no `DUMP_INCLUDES`): `-V` gives HTTPD_ROOT, SERVER_CONFIG_FILE and DEFAULT_ERRORLOG (`compiled()`), and the main file is read with its includes by `ApacheConfigFiles`. mod_status in a container is fetched inside it (often no curl there; then the error log is used). Tested with a scripted fake and, for real quoting, a stand-in `podman` script over this machine's Apache; not yet against a real container. If nothing is found, the admin can set Apache's main configuration file on the server's Apache form (`servers.apache_config_file`, full path; changing it forces a rescan): `ApacheConfigFiles` reads it and follows `Include`/`IncludeOptional` as Apache does (file, whole directory recursively, wildcards in any path component via `find -L` on the fixed base and `fnmatch` in PHP, sorted; relative to ServerRoot; loops and more than `MAX_FILES` stopped), inlining each include so `<VirtualHost>` context is kept. ServerRoot comes from the file, else the file's directory (noted); `${VARIABLES}` also come from an `envvars` file in ServerRoot (Debian; `export` lines, `$SUFFIX` empty); the version from the last "resuming normal operations" in the error log. Checked against this machine's Apache: the same 49 files as `-t -D DUMP_INCLUDES` and the same logs and mod_status URL as the control-program scan.
- Logs are read incrementally with `RemoteLogs` (shared with the MariaDB import; offsets in `servers.apache_import_state`). Error log entries (`ApacheLogParser`: 2.4 and 2.2 formats, server timezone; `notice` stored as `note` and shown as Notice, found by searching "notice"; info/debug/trace dropped; "exit signal"/segfault = crash) go to `apache_log_entries`; access log lines are summed per 5 minutes into `apache_traffic` and **each request is stored** in `apache_access_entries` (client, vhost, method, path, protocol, status, bytes, referer, user agent, time taken) for the Apache setting `apache_access_keep_days` (default 7, 0–30; 0 stores none; traffic sums are kept 30 days either way). **Every log is read in its own format**: the scan records `access_formats` (path => formats; `ApacheService::logFormats()`): CustomLog's inline format or LogFormat nickname, looked up in the line's virtual host first (nicknames get redefined per vhost and by e.g. Let's Encrypt), then the main server; TransferLog uses the scope's nickname-less LogFormat, else Common Log Format; several formats per file when vhosts share it. `AccessLogFormat` compiles a format into a line parser (%h %a %t %{strftime}t %{sec|msec|usec}t %r %m %U %q %H %s %>s %b %B %O %v %V %p %D %T %{ms}T %{Referer}i %{User-Agent}i; anything else matched and ignored; quoted fields allow `\"`, values unescaped); a line none of them match falls back to the `[time] "request" status bytes` core (with vhost:port first and combined's referer/agent when present). A request's vhost comes from %v/%V (+%p), else the one virtual host writing that file. The first import after requests started being stored backfills the log's tail once (`state.access_entries`), without touching the traffic sums. **Rotated copies** (`error.log.1`, `access.log.2.gz`, …; history from before monitoring started) are never read by the regular import; `php leaf app:apache-history SERVER` (`ApacheService::importRotated()`, holds the scheduler lock) reads each configured log's `path.N[.gz]` over one SSH login with `zcat -f` (`ROTATED_MAX_BYTES` each, oldest first), in the log's formats, adding only lines older than what's stored for that log (traffic: before its earliest bucket; requests: before its earliest request; errors are de-duplicated by hash), so running it again adds nothing; retention as usual (errors and traffic 30 days, requests `apache_access_keep_days`). Done for this machine's `localhost` server on 2026-09-29. A vhost's requests from a shared log are only its own. **fail2ban** (`Fail2banService`, `Fail2banController`, `public/assets/js/fail2ban.js`): each Apache import also reads every jail's banned addresses into `servers.fail2ban_bans` (one `sh` script over the same SSH login; asks `sudo -n -l fail2ban-client status` first so a server without the sudo rule never logs failed sudo attempts; `fail2ban_message` says why when it can't, with the sudoers line to add), and the access log colours banned clients red (`ip-banned`; the jails in the tooltip). **Right-click menus** in the access log (`public/assets/js/client-menu.js`, everyone signed in): a client address offers "Show only requests from IP" (fills the client filter; sets Localhost to any for a loopback address) and, for admins, Ban/Unban; a request's URL (`.request-path`) offers "Search for" the bare path and, with a query string, the full URL (fills the search box). A rule with conditions shows as its match, then each RewriteCond, then whether it applies. **`tests/checks/ApacheSimulator.test.php` runs the same config and 52 URLs through a real `apache2` (this machine's binary, as the test user, on a spare port) and requires identical status, Location and file.**
- **Virtual host editor** (`/admin/vhost?id=local:FILE:LINE` from "Apache on this server", or `?id=vhost:ID` from the Vhosts list for a monitored server; `VhostEditorController`, `VhostEditorService`; admins on this machine only, like the other Apache changes): fields for address, ServerName, ServerAlias, DocumentRoot, ErrorLog, CustomLog (format kept), SSLEngine and the certificate/key/chain files, and a "Redirect permanent / https://…" — each changes, adds (before `</VirtualHost>`) or removes only its own line — or the text of just that `<VirtualHost>` block (must stay exactly one section). **Values are edited as written** (`ApacheNode::rawArgs`/`rawArg()`: `${APACHE_LOG_DIR}` stays, the simulator uses the filled-in `args`), and **only lines in the block's own file count** (an `Include` inside the vhost, e.g. Let's Encrypt's `options-ssl-apache.conf`, is edited in its own file): saving the fields unchanged gives the same bytes (tested, and checked on this machine's four vhosts). The rewrite editor reads rules as written too (`RewriteRules::fromNodes(..., raw: true)`). "Try a URL" (this machine only) simulates with the unsaved change. Saving: this machine through the helper; a monitored server through **`RemoteApacheService`, which relies on the SSH user's own sudo rules** (the user's choice; nothing installed there): `sudo -n -l CMD` asks what's allowed without running it (configtest via `apache2ctl`/`apachectl` `configtest` or `-t`, `systemctl reload|restart apache2|httpd`, `apachectl graceful`, `cat`/`tee FILE`), `-n` never prompts; the file is re-read and must match the page's hash, written directly (if the SSH user can) or with `sudo tee`, via a mode-600 staging file in the SSH user's home (base64 in 60 KB chunks: a single remote command is limited to ~128 KB), then configtested and **put back if refused**; the old text is kept in `apache_admin_log.previous` (with `server_id`). The page lists what the rules allow and an example sudoers line for what's missing. Containers (`apache_container`) and scans without `config_file` aren't editable. Tested with stand-in `sudo`/`apachectl`/`systemctl` scripts through a real shell.
- `ApacheConfigParser::arguments()` (and the tree) unescape only `\"` inside double quotes, as Apache does; `stripcslashes()` used to eat regex backslashes (`\.php`).
- Script tags use `App\Utils\Asset::url('/assets/js/…')` (adds `?v=<mtime>`): Apache sends no Cache-Control for `public/assets`, so without it a browser can keep running an old copy of a changed script.
- **Blocklists** (`BlocklistService`, `blocklist_ips`, `php leaf app:blocklists`): blocklist.de's all.txt (single addresses fail2ban users report) and Spamhaus DROP (`drop_v4.json`/`drop_v6.json`, CIDR ranges) are downloaded once a day by the scheduler (`due()`, `REFRESH_HOURS`) into `storage/app/blocklists/` (`<name>.txt` normalised, `status.json`; a failed download keeps the previous copy) and checked locally — no client address is sent anywhere. Each distinct access-log client gets a `blocklist_ips` row (`sources`, null when on no list): new ones after each Apache import (`checkNew()`), all again after a download (`recheckAll()`, which also forgets addresses no longer logged). The access log colours listed clients amber (`ip-listed`; banned red and protected green win), names the lists in the tooltip, and filters on them (`listed` in/out, a subquery on `blocklist_ips`). Tests pass a scratch directory and a stand-in download (`new BlocklistService($dir, fn ($url) => ...)`), never the network.
- **Request IDs** (`extras/apache/enable-unique-id.sh`, README there): mod_unique_id's ID appended to access (`%{UNIQUE_ID}e`) and error (` [id %L]`, via an `ErrorLogFormat` identical to Apache's default for the MPM) log lines, and sent in every response as `X-Request-ID` (`Header always set`, mod_headers enabled if needed; `--undo` keeps mod_headers when other configuration needs it). At the end of the line because fail2ban's stock `apache-auth`/`apache-noscript` stop matching anything between `[pid]` and `[client]`; the script refuses when `apache-badbots`, `apache-pass`, `apache-botsearch` or `apache-shellshock` (end-anchored) jails are enabled. **sys stores the ID** (`request_id` on `apache_access_entries` and `apache_log_entries`): `AccessLogFormat` reads `%{UNIQUE_ID}e` and `%L`, the fallback a trailing ID-shaped word after the user agent (not end-anchored, so formats with more fields still parse), and `ApacheLogParser` takes `[id …]` out of the error message (`RemoteLogs::store()` writes the column only when the parser gives one, so MariaDB entries are untouched). In the reports an error with an ID has **Show request** (a `data-paged-find` button: the access log clears its filters, searches for the ID — search matches `request_id` exactly in both — and scrolls into view), and a request with errors has **▸ N errors**, which folds out a row under it with those entries (`accessPage()` returns `errors`, counts, and `error_entries`, up to `ApacheReportService::ERRORS_PER_REQUEST` (20) each, oldest first; `data-fold-toggle` in `paged-table.js` toggles the `tr.fold-row` after the button's row), with "Find them in the error log" (`data-paged-find="#error-log"`). Test it without root with `APACHE_ETC` (a copy of /etc/apache2) and stand-in tools in PATH.

## SSL monitoring

A **certificate** (`ssl_certificates`) has a name (free text, e.g. "Main site") and the hostnames it should cover (the first is sent as SNI and can't be a wildcard). **Bindings** (`ssl_bindings`) say where it's served: a server and port, or directly via DNS (`server_id` null). Several servers can serve the same certificate, and one server can serve several on different ports. Admins add certificates on `/admin/ssl/new` (SSL › Add, or the button on `/ssl`) and manage bindings on `/ssl/{id}`; the server form shows its bindings read-only. With no hostnames given, the name is used as the hostname. **Every other name a certificate lists (SAN) gets an entry of its own** (`SslMonitorService::addEntries()`: named after the hostname, one **direct** binding at the same port, so it's checked through DNS — a name on a certificate may not resolve or answer; wildcards skipped; an existing entry with that name or first hostname is kept; at most `MAX_NEW_ENTRIES` (100) at a time; the note says where it was found), after adding and via "Add an entry per name on the certificate" (`addEntriesFromCertificate()`: downloads the certificate from its first binding, `SslCheckService::certificateNames()`, unverified) and on every check. The `/ssl` list doesn't show hostnames; a certificate that isn't OK (warning, critical, unknown) folds out (click the row) into each non-OK binding's status and summary, OK and unchecked ones don't fold.

- **CSR tool** (SSL › CSR, `/admin/csr`, admins; `CsrController`, `CsrService`, table `csr_requests`, model `CsrRequest`): a certificate signing request to replace a certificate. Start from a monitored certificate (`fromMonitored()`: the one its first binding serves now, fetched unverified with `SslCheckService::certificatePem()`; also "Request a replacement (CSR)" on `/ssl/{id}`) or a pasted PEM (`describe()`: common name, SANs, subject O/OU/L/ST/C/emailAddress, key kind, issuer, expiry, SHA-256 fingerprint), which prefill the form. The private key: **an existing one pasted** (must match the certificate, `openssl_x509_check_private_key()`; used, never stored: `key_source = provided`) or **a new one** (`KEYS`: RSA 2048/3072/4096, EC P-256/P-384; the certificate's kind preselected), kept encrypted (`SecretCipher`, `csr-private-key:<id>`, hidden from serialisation) and downloaded as a file only after a fresh password/passkey check in the confirm dialog (`confirmIdentity(codes: false, passwordField: 'acct_password')`); deleting the request deletes the key. The CSR (SHA-256, names as subjectAltName) is made with a temporary openssl config of our own (`[req] default_bits` must be set even for EC keys, or PHP's `openssl_pkey_new()` refuses; it also avoids depending on the system's openssl.cnf, which PHP on Windows may not find). Downloads use `Headers::set()` (Leaf pitfall). Tested with `openssl req -text` in `tests/services/Csr.test.php`, and in a browser against badssl.com's live certificate (prefill, EC key, wrong/right password, files verified with openssl).
- `SslMonitorService` checks each binding separately: `SslCheckService::check($sniHost, $port, $connectTo, $expectedNames)` connects to the server's own hostname/IP (or resolves the hostname for direct bindings), sends the SNI name, verifies, and warns about listed hostnames the certificate doesn't cover (`covers()`: one wildcard label). Results go to `ssl_checks` (`binding_id`, 30 days); the worst status is kept on the binding, the certificate and the server (`last_ssl_status`), and recomputed when a binding or certificate is deleted.
- Every check (so the daily scheduled one too) adds entries for names the certificate lists (SAN, `details.names`) that have none, only when the check wasn't critical (an invalid certificate could be anyone's); SSL setting `ssl_import_names` (1/0, default on). A certificate's own hostname list is no longer extended automatically.
- `convertLegacy()` turns the old per-server `ssl_hosts` lists into certificates and bindings (runs when `/servers` loads).
- The CA bundle comes from `CaCertificateService::systemBundle()` (`composer/ca-bundle`): the system's (`openssl.cafile`, `curl.cainfo`, `SSL_CERT_FILE`, usual Linux paths), else the bundled Mozilla list. PHP on Windows has no system bundle file, so it uses the bundled one; certificates from an internal CA then show as untrusted unless `openssl.cafile` points at a bundle that includes it.
- Two TLS connections via `stream_socket_client` with SNI: one fully verified (the CA bundle above, or a CA file passed to the constructor, which tests use) gives the verdict; when that fails, one unverified connection reads the certificate to explain why. The judgement is a pure `evaluate()`.
- Verified PHP behaviour: a hostname mismatch gives a specific "Peer certificate CN=... did not match" warning, but expired, self-signed and untrusted certificates all give only "certificate verify failed", so `evaluate()` works out the reason from the certificate itself. TLS errors arrive as PHP warnings; `SslCheckService` collects them with a temporary error handler (Leaf would otherwise turn them into 500s).
- **Missing intermediate certificates**: a server that sends only its own certificate fails OpenSSL's verification (and curl, PHP, Java, some phones), while browsers fetch the intermediate from the certificate's AIA "CA Issuers" address and show the site. When verification fails (not for a name mismatch), `SslCheckService::completeChain()` does the same: downloads that intermediate (`download()`: plain http, every resolved address public — no private, loopback, link-local or reserved ranges — connecting to the checked IP with a Host header, 5 s, 20 KB, no redirects; cached per checker), then verifies with `openssl_x509_checkpurpose(leaf, SSL_SERVER, [CA bundle], intermediate-as-untrusted)` and checks the name. If that works the certificate is valid with a note saying the check had to download the intermediate (from where) and to send the full chain; SSL setting `ssl_missing_intermediate` (0 Info — stays OK, the default; 1 Warning; 2 Danger/critical) sets its severity. Found on www3.calpers.ca.gov (Sectigo OV R36 not sent); tested with a real `openssl s_server` serving only the leaf.
- An invalid certificate (expired, wrong name, untrusted, unreachable) is critical. A valid one is a warning once it expires within the warning period (days left <= `ssl_warning_days`, an admin setting, default 7), never critical. Checked against badssl.com (valid, expired, wrong host, self-signed, untrusted root, incomplete chain) with the expected verdicts.
- Test certificates made with PHP's `openssl_csr_sign` need `'digest_alg' => 'sha256'`, or OpenSSL servers refuse them ("ca md too weak"). `tests/checks/SslCheck.test.php` starts real `openssl s_server` instances.
